A CLI-only version installs an already published catalog, so the engine packages and existing frozen assets keep their pins. Run it with `gh workflow run release.yml -f build_run=<main build run id> -f scope=cli`.

**CI scope:** pull requests run only what their changes affect (`scripts/affected.mjs`): changes confined to `packages/cli` run one Ubuntu job that typechecks, tests, packs the CLI and installs it into clean web and React apps against the latest published runtime release; documentation alone runs nothing; anything else runs the full graph. Pushes to main always run the full graph, so release builds keep complete acceptance. Pull requests reuse their own native build caches.

# Runtime release preparation

The runtime repository owns the portable contract, engine, adapters, installer and conformance tests. The product owns SVG/font compilation, authoring schemas, agent tools, prompts, generation, brand analysis, visual review/correction, editor behavior and hosted services. The codec encoder serializes already-compiled portable data; it does not create artwork. The hosted Chocopie product consumes exact npm versions and Swift Package releases. Keep sibling checkouts for development and test packed artifacts before updating the product lockfile. Do not use a product Git submodule or copy a runtime per moment.

CI builds from a clean checkout with no product repository or secrets. Pull requests run TypeScript, codec/corpus tests and native/WASM checks. Build receipts identify compilers, backend patches and artifact digests. Only synthetic conformance artwork is redistributed here; the private product retains its real-gallery acceptance suite.

The preparation workflow uploads npm tarballs, hashes, source/build provenance and native SDK artifacts for review. The release workflow is manual, checks `release-gates.json`, validates the selected version against package manifests, and uses the protected `release` environment. It must publish the exact reviewed tarballs, not rebuild them during publication.

Android preparation uses `scripts/choco/build-android-package.sh` to stage the JNI library, Kotlin host and `ANDROID-BUILD.json` receipt. `scripts/choco/build-rn-package.sh` checks the Android ABI/source hashes alongside the iOS slices before packing the combined development artifact. A source adapter is not a supported-platform claim: Release Fabric and Expo consumers must execute with bundled offline assets, all controls, independent players, lifecycle/error checks and identical native/WASM fixture pixels. Record the actual API, ABI, NDK and device in the evidence. Physical-device startup/frame/memory/energy and minimum-OS/API acceptance are recorded follow-up checks, explicitly deferred for the first release rather than marked passed. Desktop currently has native core/frame tools only, with no packaged application UI adapter.

Distribution: npm for web, React Native and CLI; GitHub Releases for the XCFramework ZIP and provenance; a tagged Swift Package manifest resolves that ZIP by SHA-256. No hosted service is needed by installed players. Documentation can live in this repository initially; no separate deployment is needed for playback.

For each release, complete the release gates. The five package manifests are publishable; the workspace and synthetic consuming applications remain private. npm trusted publishing is configured for `Chocopie-Moments/runtime`, workflow `release.yml`, environment `release`, using GitHub-hosted runners. No registry token is checked into this repository. Only reviewed clean-main bytes are published. Preparation CI only packs artifacts.

Public source can precede supported binaries, provided the README and package status remain explicitly unreleased. The founder has also authorized product cutover; source availability alone does not satisfy its artifact and acceptance checks. The product cutover follows installed-app/browser verification and package availability.

Verified development iOS profiles: bare React Native 0.87.1, and Expo 57.0.17 / React Native 0.86.3 / React 19.2.3. The Expo iOS Release simulator executed eight offline/lifecycle/controls/error checks; this does not verify Android, physical devices or other Expo versions. The CLI admits only these installed native profiles and uses `expo/metro-config` for a new Expo Metro configuration. Run `node packages/cli/test-native-installed.mjs release expo` to exercise the packed Expo installer offline (cached npm dependencies required); this command does not build or execute native code. Repack the reviewed RN artifact after changing peers; no legacy-peer-deps override is part of the supported profile.

CI explicitly prepares npm resolution metadata with `node scripts/prepare-package-cache.mjs` after packing and checking artifact hashes. This temporary online install is preparation only; `npm run check:packages` and the generated web/React installer consumers retain their offline installation and playback checks. A workspace `npm ci` alone caches lockfile tarballs without necessarily caching the registry metadata needed to resolve a new consumer manifest.

After the reviewed runtime checkout is clean, prepare a history-free local source review artifact with `node scripts/prepare-publication-baseline.mjs /absolute/NEW-private-directory`. It exports only tracked HEAD blobs, enforces runtime source/package ownership roots, verifies fixture manifest paths, requires all packages private and release readiness false, excludes generated/untracked files and produces a SHA-256 source archive plus per-file manifest. The default does not initialize Git. Optional `--init` additionally creates a new local repository with one Conventional Commit and no remote; existing history/stashes are never copied. Path inventory checks do not replace source, fixture provenance, notice or publication approval review. The reviewed history-free baseline is approved for source publication; any subsequent source snapshot still requires ownership, fixture and notice review.

The first public release must be rebuilt from the approved clean source history. Existing private CI artifacts and Swift tag plans retain their actual private source ancestry; their validation evidence is useful, but those commits and tags must not be pushed into the history-free public repository. A manifest-only Swift commit still carries its parent's entire history. After publishing the approved clean source, run the normal preparation workflow from its main branch, review the new artifact hashes and Swift plan, and update the product's exact pins before cutover. Keep successful-main-build provenance and publication checks intact; do not relabel older artifacts with the clean baseline's commit.

General artifact preparation now calls the Android proof workflow at the same source revision before staging native distribution. Its JNI slices, canonical Kotlin source hashes, renderer patches, NDK notices and independent SDK AAR hash are admitted before restoration. The iOS build then packs one RN tarball containing both platforms. `stage-native.py` requires those platform receipts and compares the AAR's embedded Android build receipt and exact JNI bytes against the combined RN package. The reviewed release includes the AAR and SDK receipt, without proof APKs. This assembly does not certify Android device execution.

The release catalog itself now has an exact digest in `artifacts.json`. Publication checks that digest, catalog source and package pins, combined RN platforms and the independent AAR before any npm write. The existing private-package, clean-source, matching successful main build and closed release-gate checks still apply. Approved tagged Swift Package preparation, mandatory postpublication Swift acceptance and actual device acceptance remain unfinished; no publication is enabled by these preparation changes.

The general workflow also runs the exact packed runtime in pinned Playwright Chromium, Firefox and WebKit on Ubuntu, one engine at a time. It reuses `scripts/browser-checks.mjs`, serves the installed tarball's runtime files and synthetic fixture bytes, blocks browser requests to external services, bounds each diagnostic to 30 seconds and records versions, checks and the artifact digest. This closes only the functional checks actually recorded by a successful run. Headless checks do not establish physical Safari behavior, performance, or page-hidden/foreground transitions; offscreen and explicit suspension are exercised.

Swift preparation creates an XCFramework-only ZIP, its exact release URL/checksum, and a root `Package.swift` using the existing SDK sources at `native/ios/Sources/Choco`. `node scripts/prepare-swift-tag.mjs release` creates a deterministic **local commit object** with the reviewed artifact source as its parent and only that root manifest changed; it moves no ref, creates no tag and performs no remote write. The uploaded `swift-tag-plan.json` is unapproved review evidence. After all release gates and the owner approve, the intended tag must be pushed separately at that exact manifest-only commit. Publication preflight requires that existing lightweight remote tag and checks its exact commit before the first npm write; `gh release create --verify-tag` then attaches only the validated flat receipt allowlist. It does not silently tag the original source without a Swift manifest. Prepublication admission reviews the manifest, exact ZIP checksum and existing approved tag. Actual remote Swift resolution requires the released ZIP, so it runs after asset publication and remains mandatory before product release or cutover. The macOS acceptance job in `release.yml` downloads and hashes the actual released binary, resolves the tagged package, checks the exact checkout commit and installed binary target, and only then attaches `release-acceptance.json`. A failed check leaves no accepted receipt. Product release configuration must pin this receipt by SHA-256 and independently verify that its matching `release.yml` workflow-dispatch run completed successfully; an available catalog alone is insufficient. No current publication gate is declared passed by this ordering change.

Before the first write, publication also checks that every npm family version and the GitHub release are absent. Only explicit registry/GitHub 404 responses establish absence; network and authorization failures stop publication. This reduces predictable partial publication but does not make independent registries transactional. If a write fails after another succeeds, stop and have the release owner review the immutable published bytes and recovery plan; the workflow does not blindly retry or replace them. Initial package-name ownership and trusted-publisher setup remain account-owner steps.

The account owner must bootstrap previously nonexistent npm names before configuring trusted publishers. npm documents that `npm trust` requires an existing package; an explicitly approved first staged publication creates a public `0.0.0-stage` placeholder. That is a public write covered by the founder’s current publication authorization; it still requires the account owner and must not be confused with an already completed release. Configure each package for repository `Chocopie-Moments/runtime`, workflow filename `release.yml`, environment `release`, and explicitly allow `npm publish` (new configurations permit staging by default). Newly configured trust must complete its first successful publication within two days. See the official [npm trust requirements](https://docs.npmjs.com/cli/v11/commands/npm-trust/), [staged-publication behavior](https://docs.npmjs.com/staged-publishing/) and [trusted-publisher configuration](https://docs.npmjs.com/trusted-publishers/). Bootstrap, trust setup, approved tagging and publication must be recorded as actual release actions; preparatory documentation does not establish that they happened.

`release-gates.json` readiness records the authorized first-release source and scope. It does not claim completed publication, npm account/trust setup, Swift tagging, or deferred device verification. The exact successful clean-main build, reviewed artifact integrity and approved remote Swift tag are required before publication; account setup is an owner prerequisite. Remote Swift resolution and its accepted receipt remain mandatory before product cutover. Physical and minimum-OS/API measurements remain `verified: false` even when source/scope readiness is true.
